1. 先看结论

目前已经从“改变外边界温度”推进到“相同外边界、相同密度 EOS 下改变指定 T–P 曲线”，并完成一个局部合成气层质量恢复案例。第五阶段的论文大气廓线接入尚未开始。

  • 新 TP 实验的固定输入：5 地球质量，表面 0.1 bar / 300 K，无水层，固体核/幔质量比 0.325/0.675；气体统一使用原有 Gas(mu=2,n=2) 工程夹具。
  • 曲线 A：T=300+30 ln(P_bar/0.1)；曲线 B：T=300+40 ln(P_bar/0.1)。同为 1% 气层时，B 相对 A 半径增大约 236.642 km（2.11747%）。
  • 原方向：以 B 的半径为目标、用 A 恢复组成。预设气层分数 0.002—0.08 的两个端点不包围目标，整项合同 FAILED，没有恢复组成。不能据此断言内部没有根。
  • 后续反向案例：以 A 的 1% 气层为真值、用 B 拟合，恢复 0.2436038778% 气层，偏差 −0.756396 个百分点，相对低估 75.6396%。名义半径相对残差约 2.0373e-8；相同组成的收紧容差和节点细化对照通过。
  • 反向方向是在看到原失败后选择的，属于事后选择的局部工程验证，不是无偏调查或原失败结果的改写。
  • 新 TP 合同累计 14 次完整拟合（原 8 + 新 6，含 OFF 对照）；DeepSeek 接口实现调用 44/44。反向恢复新增 API 调用 0，新增 C++/EOS 修改 0。本次总报告只读取归档、核对链接和哈希，不运行模型。

以上说明热结构假设能够在这个合成夹具里造成明显的组成恢复偏移；不能直接转化为真实亚海王星的组成结论。

TP 接口具体改了什么

输入为 P_bar,T_K，正有限、严格递增压力、至少两行；内部转cgs单位。采用 T 对 ln(P) 线性插值，越界直接失败，禁止静默外推。可选 tp_profile_file 不给时走旧路径。

气体被明确固定为 gas_fixed_mu2。这样避免 gas_default 在100 bar两侧同时把分子量3变2、等温变绝热的混杂；不靠移动该切换压力伪造纯热实验。密度计算、积分右端和实际接受状态使用同一 T(P)，不同时强制原绝热热方程。跨节点控制步长并重置步进状态；拟合点严格放到非气体区域。气层底部连续温度会影响固体内部，因此结果包含耦合内部响应。

输出 .tp.json 保存高精度实际 P/T/密度/质量、原始匹配残差、覆盖范围、气层底部和修正状态。独立检查核对实际组成、EOS身份、边界与原始残差；只改最终输出温度不能通过验收。CLI 对无效输入与旧成功侧车文件实施失败关闭。

v1 主要限制：mode0、四个组成槽、气体至少1g且存在非气体、三个层间温差为0；部分路径格式如含空白/UNC不支持。Gas(mu2,n2) 只是工程夹具，不是目标行星的物理气体EOS验收。

为什么原方向没有完成反演

A 在气层分数0.002和0.08时的半径都小于 B 的目标半径，预定括区间不成立，故0次二分且没有推断组成。A 在0.002、0.01、0.08三个样本上也非单调递增；不能默认“多加气一定增大总半径”。气层加厚与固体压缩/热状态变化存在耦合。

A 的8%气体案例底部约45.58 GPa、760 K，理想气体密度约14.53 g/cm³，高于邻接固体约4.71 g/cm³。这提示夹具物理适用性问题，不能单凭它证明代码bug或动力学不稳定。没有通过调阈值把这轮失败变为成功。

反向恢复是怎样验收的

先在提交 223374d 固定新合同，保留原A/B、真值、边界和求解器，仅交换真值/拟合方向并使用带符号局部括区间搜索。复用的旧结果通过提交与哈希验证，不再运行；新4次搜索和2次最终确认均留存实际输出。

恢复的带符号数值括区间为 [0.0024303854921362464, 0.0024360387783536647]，宽约5.6533e-6；名义根同时满足半径残差≤5e-6和区间宽≤2e-5。收紧容差与共线节点细化分别保持同一恢复组成，半径相对名义变化约2.12e-11和1.62e-11；细化曲线实际加载了10个节点。全部新案例通过原残差、覆盖、组成和错误相图等检查，以及气/固密度支筛选。

真值气层质量0.05 M⊕，恢复约0.01218019 M⊕，有符号差约−0.03781981 M⊕。括区间是数值求根证据，不是置信区间；没有证明唯一解或未采样范围的行为。密度筛选通过也不是EOS物理有效性认证。

5. 开发过程中确实遇到的问题

这项工作不是一次生成就通过。独立审核先后提出修改要求，返修后的具体源码和实际检查才获得限定范围批准。

  • Cline 最初长时间规划后仅生成桩文件，终止该次执行；保存状态是 act 模式，不能把原因确定为误入 plan 模式。随后使用已有同模型官方API和限定编辑任务，无需重复安装或认证。
  • 一次推理参数尝试耗尽18000推理token，返回长度上限而无可用内容；没有把这种调用算为有效修复或科学结果。没有统一可核对的全项目token/费用账单，本报告不捏造总费用。
  • 私有临时源副本曾被模型片段错误整体覆盖，原研究仓库与公开科学基线未受该事故修改；从保留响应恢复，并增加调用前快照、禁止既有大文件整体替换、编辑重叠与唯一锚点检查。原始模型响应仅私有保存，不公开密钥或会话。
  • 实际审查纠正过旧温度参与密度、选相早于温度投影、步进器未重置、质量/长度单位误比、OFF旧修正路径回归、提前截断被接受、失败状态/原因丢失、诊断遗漏错误相图气行和缺少边界锚点等问题。详见实施台账和分阶段证据，不能将早期版本视为最终版本。
  • 达到32次额度后，用户明确批准最多再12次，总上限44。44次用尽后，用户仅明确允许Codex直接修一个重复TP选项触发错误前清理旧诊断的局部顺序问题；该修改也经过独立复验。没有据此扩大为Codex接管科学实现。
  • 首轮恢复未括根时停止并原样封存；后续在用户继续指令下另立合同。控制器和缓存绑定实际组成、源文件、求解器及运行时EOS表身份，避免把旧缓存/错质量结果误当新结果。

工程、科学归档和工作流放在同一个仓库，提供 README/START_HERE、AGENTS分工、短规则、TP验收表、状态文件、固定检查控制器、预算/停止原因和断点恢复、外部密钥路径配置、离线样例、问题模板。参考项目与设计来源单独列在来源文档，保留MAGRATHEA上游署名与MIT许可。

已记录的工作流验证：Windows Python 3.12与WSL Python 3.14各66测试通过，分别4/2项权限或平台跳过；新克隆完成doctor、三个依赖节点、状态和二次恢复，0模型调用。provider适配器有mock测试；没有完成这个新便携运行器的真实DeepSeek→Codex端到端验收。本轮TP实际开发使用私有受控调用脚本与公开的确定性数值控制器，不能声称全由portable.py自动编排。远端CI结果也未由这些本地检查证明。
